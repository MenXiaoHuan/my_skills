# Test Design Methods

本文件是详细 case 设计方法的唯一权威。

## 通用质量

先建立 `业务目标 → 核心流程 → 失败风险 → 验证意图 → 可观察断言`。每个 case 只验证一个意图，前置条件只描述角色、权限、数据、状态和环境；case 不得依赖另一 case 的执行结果。

关键步骤写明入口、操作对象、必要输入和触发动作。预期写明观察对象以及状态、数据、权限或错误处理结果。异常 case 同时检查反馈、数据不变性以及适用的补偿或恢复行为。

## 交互与工作流

覆盖入口、默认状态、主要动作、合法后态、返回或取消、重复操作和关键失败分支。子页面、弹窗、抽屉和标签页保留父工作流归属。相同意图和断言面的轻量展示检查可以合并，避免按每个控件拆成薄 case。

## 决策表

多个业务条件共同决定结果时，列出条件、结果和例外。合并等价规则，覆盖每个不同结果和高风险条件交互，不穷举无业务意义的笛卡尔积。

## 状态迁移

覆盖每条高风险合法迁移、关键非法迁移、终态、撤销或回退以及并发迁移。前态、动作、后态或可恢复性不同的迁移使用独立 case。

## API 契约

仅根据接口证据生成：

- 方法、路径、鉴权和权限
- 必填、可选、类型、枚举与边界参数
- 状态码、业务错误码和响应字段
- 幂等、重复请求和并发竞争
- 超时、重试、限流和依赖失败
- 数据库、缓存、消息、回调、下游和回滚副作用
- 版本与字段兼容

业务动作是主步骤，必要的 API 请求、响应和副作用是可观察验证。不要机械地把每个业务 case 改成纯接口测试。

## 数据一致性

每个 case 明确：

- 左右对比对象
- 连接键
- 数据范围和快照
- 强一致或最终一致
- 观察时机与允许延迟
- 可观察断言

典型关系包括 UI/API/详情/导出一致，成功数加失败数等于总数，重复请求不产生重复记录或消息，筛选分页与导出范围一致，以及终态与存储、缓存、消息和下游状态一致。

## 组合与边界

先做等价类和边界值；业务条件使用决策表；状态行为使用状态迁移；独立参数默认 pairwise；高风险交互按风险选择更高强度的 `t-way`。来源明确禁止的组合不进入候选。

每次扫描阈值、时间窗、枚举边缘、空值、极值、重复和并发。只有存在真实业务或契约边界时才生成独立 case，不为增加数量制造薄边界 case。

## 异常与恢复

存在外部依赖或异步链路时，考虑超时、失败、部分成功、重试、幂等、回滚、补偿、降级、回调丢失和最终一致性。期望必须同时描述用户反馈和系统状态；不能只写“处理成功”“返回正确”或“符合预期”。
