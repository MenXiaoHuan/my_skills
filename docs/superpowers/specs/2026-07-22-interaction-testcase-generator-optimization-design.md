# 交互测试用例生成 Skill 优化设计

## 背景

`interaction-testcase-generator` 已具备用例分组、双候选生成、覆盖账本、优先级标记和 XMind 输出能力，但仍存在两个直接影响交付质量的问题：

- `前置条件`、步骤动作和步骤预期可能以中文句号 `。` 结尾，导致 XMind 节点风格不统一
- 当前生成与评测更关注结构完整和场景数量，尚未强制建立业务目标、业务风险、验证意图与可观察断言之间的追踪关系

本次优化同时解决确定性的展示格式问题和影响用例有效性的业务质量问题

## 目标

- 最终 XMind 中的前置条件、步骤动作和步骤预期不以中文句号 `。` 结尾
- 生成阶段能够从业务目标推导核心流程、失败风险、验证意图和可观察断言
- 高风险业务目标具备正向路径和关键失败路径覆盖
- 测试用例保持可执行、可验证、可追溯且相互独立
- 轻量评测能够发现格式回退、目标遗漏、弱断言和关键质量退化
- 保持现有 JSON schema、XMind 层级和调用方式兼容

## 非目标

- 不建设完整的需求管理或测试管理系统
- 不要求在最终 XMind 中展示内部双候选草稿、覆盖账本或裁决过程
- 不机械要求每个低风险目标都有异常、并发和边界用例
- 不引入新的第三方依赖
- 不清理标题、分组、说明和备注中的句号
- 不移除英文句号、问号、感叹号或字段中间的中文句号

## 方案选择

采用“规则约束、构建器兜底、评测守护”的组合方案

仅修改 Skill 规则成本低，但模型输出具有概率性，无法保证最终产物稳定无句号。仅修改构建器虽然能保证展示格式，却不能改善文本输出契约，也无法覆盖文本模式交付。组合方案能够同时约束生成结果和最终文件，并通过测试阻止后续回退

业务质量采用轻量追踪模型，不修改用户可见 JSON schema。目标、风险和验证意图作为生成阶段及覆盖账本中的内部分析信息，最终仍交付现有标准化 case tree，避免破坏模板、构建脚本和既有使用方

## 标点规范

### 适用字段

以下字段末尾不得保留中文句号 `。`：

- `case.preconditions`
- `case.steps[].action`
- `case.steps[].expected`

### 清理规则

- 先去除字段首尾空白
- 删除末尾连续出现的一个或多个中文句号
- 删除句号后再次去除末尾空白
- 保留字段内部的中文句号
- 保留英文句号及其他标点
- 非字符串值沿用现有容错逻辑转换或忽略，不扩大数据模型

示例：

| 输入 | 输出 |
|---|---|
| `用户已登录。` | `用户已登录` |
| `提交订单。。 ` | `提交订单` |
| `接口返回成功。订单状态更新为已支付。` | `接口返回成功。订单状态更新为已支付` |
| `调用 API v2.` | `调用 API v2.` |

### 双层保障

生成规则要求模型直接输出无末尾中文句号的字段，保证 JSON 文本模式和 XMind 模式一致

`xmind_build.py` 在渲染前对三个字段执行确定性清理，保证旧 JSON、人工 JSON 或模型偶发违规不会污染最终 XMind。构建器不回写输入对象，避免调用方数据被隐式修改

## 业务目标模型

### 推导链路

生成前内部建立以下链路：

`业务目标 → 核心流程 → 失败风险 → 验证意图 → 可观察断言`

每个元素的定义如下：

| 元素 | 定义 | 示例 |
|---|---|---|
| 业务目标 | 功能或变更需要达成的业务结果 | 用户只能为有效订单完成一次支付 |
| 核心流程 | 达成目标所依赖的用户或系统路径 | 创建支付单并确认支付结果 |
| 失败风险 | 目标未达成时的业务后果 | 重复扣款、订单状态错误 |
| 验证意图 | 单个用例需要证明或否定的事实 | 相同支付请求不会产生第二笔扣款 |
| 可观察断言 | 能从界面、接口、状态或数据侧验证的结果 | 返回同一支付结果且支付记录只有一条 |

### 目标识别

优先从需求目标、成功指标、验收标准、核心流程、状态机、权限规则、接口契约和技术风险中识别业务目标

若材料只描述页面或接口能力，应从明确行为中提炼最小可信目标，不推测未提供的商业规则。缺失信息若影响核心流程、角色、状态、契约、预期结果或发布风险，应提问或输出 `draft`；次要信息缺失时使用明确假设

### 目标分类

业务目标至少按以下维度扫描：

- 核心业务真值
- 核心流程可达性
- 权限与数据隔离
- 状态流转正确性
- 跨系统与数据一致性
- 失败恢复与数据不变性
- 运营效率或用户体验

分类用于防止遗漏，不要求每个需求机械生成全部类别

## 用例生成规则

### 目标覆盖

- 每个核心业务目标至少映射一个用例
- 每个高风险目标至少包含一个正向用例和一个关键失败用例
- 中低风险目标根据业务语义决定是否增加异常、边界、并发或兼容性用例
- 覆盖账本记录目标、风险、覆盖用例和有理由跳过的场景维度
- 不为追求数量生成无法追溯到目标、风险、规则或契约的薄用例

### 可追溯性

每个用例在内部分析中关联至少一个来源：

- 需求条款或验收标准
- 页面、模块或核心流程
- 状态规则或权限规则
- API、数据或架构契约
- 已识别业务风险
- 明确标记的假设

最终 XMind 不强制展示追踪元数据，但标题、说明、前置条件、步骤和预期必须能够体现对应验证意图

### 前置条件

- 只描述角色、权限、数据、状态和环境准备
- 不包含点击、输入、提交、调用或校验动作
- 能够独立构造，不依赖其他用例先执行
- 无特殊准备时使用统一的无前置条件文案
- 末尾不使用中文句号

### 步骤

- 每一步只表达一个连续且可执行的操作
- 关键步骤包含入口、操作对象、必要输入和触发动作
- 不把多个无关业务动作合并为一个步骤
- 末尾不使用中文句号

### 预期结果

- 明确验证对象、状态或数据变化
- 在有时序要求时明确发生时机
- 异常场景验证错误反馈、数据不变性、补偿或恢复路径
- 跨系统场景验证必要的存储、缓存、消息、回调或下游结果
- 禁止仅使用“展示正常”“返回正确”“处理成功”等不可独立判定的表达
- 末尾不使用中文句号

### 状态与一致性

存在状态机时，覆盖合法流转、关键非法流转、重复操作和必要的恢复路径。存在外部依赖或异步链路时，检查部分成功、超时、重试、幂等、回滚和最终一致性，但仅输出有来源或风险依据的用例

### 优先级

继续使用现有 `P0/P1/P2/P3` 模型，并增加分布自检：

- `P0` 必须能够说明发布阻断、核心业务真值、严重权限泄漏、数据损坏或不可恢复跨系统错误
- `P1` 必须对应高价值流程或显著业务影响
- 若大多数用例都为 `P0/P1`，重新检查是否把可见性或一般重要性误判为高风险
- 目标风险、影响范围和可恢复性必须与优先级一致

## 文件改动

### `SKILL.md`

- 在默认工作流中加入业务目标和风险提取
- 将覆盖账本扩展为目标与风险追踪入口
- 在 Guardrails 中加入业务目标覆盖、用例独立性和字段末尾标点规则
- 保持双候选与最终单一裁决结果不变

### `references/output-rules.md`

- 明确三个字段不得以中文句号结尾
- 描述文本模式与 XMind 模式的一致性要求
- 保持 schema 和 XMind 节点结构不变

### `references/quality-rules.md`

- 增加目标、风险、验证意图和断言链路
- 增加前置条件独立性、状态流转、失败不变性和跨系统一致性规则
- 增加优先级分布和弱断言自检

### `references/coverage-ledger-rules.md`

- 增加业务目标与风险映射
- 要求高风险目标具有正向和关键失败覆盖
- 允许对不适用的异常、边界或并发维度给出跳过理由

### `templates/xmind_input.template.json`

- 将示例文本调整为无末尾中文句号
- 增加简短注释，说明适用字段的标点约束
- 不增加必填 schema 字段

### `scripts/xmind_build.py`

- 新增专用的末尾中文句号清理函数
- 仅在渲染前置条件、步骤动作和步骤预期时调用
- 不复用标题清理函数，避免扩大影响范围

### `scripts/test_xmind_build.py`

新增以下测试：

- 清理前置条件末尾一个或多个中文句号
- 清理步骤动作和步骤预期末尾中文句号
- 保留字段内部中文句号
- 保留英文句号和其他标点
- 不清理标题和备注末尾中文句号

### 轻量评测

在 `check_case_tree_quality.py` 中新增指标：

- `trailing_chinese_period_count`
- `business_goal_coverage_rate`
- `high_risk_goal_path_coverage_rate`
- `unobservable_expectation_count`
- `precondition_action_leak_count`
- `priority_distribution`

格式指标可以直接从标准 case tree 计算。业务目标与高风险路径覆盖指标从带有评测元数据的 case fixture 计算；没有评测元数据的现有 fixture 不被误判为失败

在 `baseline.json` 中为代表性案例增加最小目标和风险期望，覆盖核心流程、权限、状态、跨系统一致性和异常恢复。轻量评测不恢复已删除的完整 runtime、comparative 或 stability suite

## 验证方案

### 单元测试

运行：

```bash
python3 -m unittest skills/interaction-testcase-generator/scripts/test_xmind_build.py
```

必须验证所有新增标点规则以及现有分组、优先级和备注渲染行为

### 基线评测

运行：

```bash
python3 eval/skills/interaction-testcase-generator/.tools/validate_benchmark.py
```

必须验证现有结构质量、覆盖账本和产物内容基线，同时新增标点与业务质量指标

### 格式检查

对变更中的 Markdown、JSON 和 Python 文件执行项目已有格式要求。Python 文件不得产生或提交 `__pycache__` 与 `.pyc`

### 回归检查

- 现有 JSON fixture 无需迁移即可生成 XMind
- XMind 的根节点、分组、用例、前置条件、步骤和预期层级保持不变
- 优先级文本前缀和 marker 映射保持不变
- 自动合并共同父节点行为保持不变
- 文本模式仍返回单个标准化 JSON case tree

## 验收标准

- 所有新增和现有测试通过
- 最终 XMind 中三个目标字段的末尾中文句号数量为零
- 字段内部中文句号和英文句号不被误删
- 标题、分组、说明和备注不受清理逻辑影响
- Skill 明确要求建立业务目标到可观察断言的链路
- 高风险目标必须有正向与关键失败覆盖或明确缺失说明
- 评测能够识别目标遗漏、弱断言、前置条件混入动作和优先级异常
- 不新增第三方依赖，不改变既有 JSON schema 和 XMind 层级
- 仓库中不包含临时文件、`__pycache__` 或 `.pyc`
